# 核验场景

## 场景一：一行包含多个动作

输入的一行员工记录同时包含上午、下午、序号、分号、休假和多个独立动作。

预期行为：保留原始记录ID；按语义动作拆分，而不是把整行算作一个任务；单独分类休假；每个信号绑定原文；不得生成周度或月度结论。

## 场景二：缺少换算规则但要求评分

预期行为：展示七维证据并设置 `numeric_score: unavailable`，不得只根据权重生成 0—100 分。

## 场景三：岗位和结果不明确

预期行为：列入岗位待确认清单；只提取过程证据；不得声称项目完成、产生收入、完成验收或给出绩效排名。

## 场景四：半天请假、半天正常工作

输入：员工上午请假，下午填写一项有效工作任务。

预期行为：识别为半天请假、半天出勤；应工作时段数为1；下午工作时段覆盖率为100%；上午不计入未填；不得因只有一个工作时段或事项数量较少判定工作不饱满；请假不计入任务数和项目工作量。

## 场景五：半天请假、另一时段未填

输入：员工上午请假，下午没有有效工作任务。

预期行为：只将下午标记为应工作时段未填；不得把上午请假重复计为未填；不得把人员标记为全天无故未填。

## 场景六：请假时段不明或数据冲突

输入A：只填写“请假”，未说明全天、上午、下午或起止时间。输入B：出勤状态标记全天请假，但上午和下午都有工作任务。

预期行为：输入A设置 `leave_period_review_required=true`，不计算工作时段覆盖率；输入B设置 `attendance_conflict=true` 并交人工核验；两种情况均不得自行推断或生成确定性饱满度结论。

## 场景七：模型输出证据门禁

输入：已验证的 `daily-facts.json` 与模型输出的 `daily-analysis.json`。

预期行为：模型输出只能包含 `work_summary`、`project_highlights`、`risk_items` 和 `next_day_actions`；每项使用事实包内的 `evidence_ids`。任何未知证据、人员、项目、指标改写、结构错误，或缺少风险/行动证据均拒绝输出并降级到确定性基础报告。本文档仅供人工理解；发布依据是 Python 自动测试文件。
