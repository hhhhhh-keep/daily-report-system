# 日报 AI 分析系统总体设计 v2

## 1. 定位、范围与固定架构

系统是部门内部轻量日报采集、AI 分析及管理辅助系统。员工每天通过微信群中的固定日报填写链接提交信息；系统结构化保存人员、项目和工作事项，定时分析人员效能、项目风险与资源协同，生成管理视图、分析报告并发送邮件。AI 仅提供分析和建议，不自动调配人员或替员工、管理员作出项目决策。

固定架构为一个 **Vue 3** Web 工程 `daily-web`、一个 **Spring Boot** 后端和 **PostgreSQL** 数据库。后端保持模块化单体（**modular monolith**）：各模块以应用内接口和领域事件协作，共享受控事务边界，不拆分为独立服务。交付使用 **Docker**。

第一阶段不建设审批、客户关系管理、绩效管理、工时系统、员工账号体系、多角色权限、独立服务拆分、外部消息中间件、容器编排集群或外部流程编排工具；不采用 n8n 类流程工具。也不建设复杂审计或复杂链接安全机制。

## 2. 前端、访问与最终拓扑

### 单一前端工程与路由

`daily-web` 是唯一的 Vue 3 工程，同时适配手机填写页和 PC 管理后台：

| 路由 | 用途 |
| --- | --- |
| `/report` | 员工手机日报填写页，由微信群固定地址进入。 |
| `/my-report` | 员工当天日报查看和修改页。 |
| `/admin/*` | 管理后台，覆盖驾驶舱、日报、分析、基础数据、配置与任务记录。 |

不再把填写端与展示端拆成独立前端工程或独立镜像。`/report` 是微信群中的 **fixed report link**，入口无需员工登录（**no employee login**）；第一版接受“选择的姓名不一定能严格证明实际填写人”的内部工具取舍。姓名加日期用于找到并维护当日记录。

管理端仅有一个 **single administrator account**，路径为 `/admin`。支持用户名密码登录、密码安全散列（**password hash**）存储、Session/JWT、修改密码与退出登录。不存在角色分配、多管理员角色、单点登录、第三方授权登录或权限矩阵。

保留必要保护：HTTPS、管理密码及密钥不写入日志、后端受限连接 PostgreSQL、提交/当天修改/配置变更/任务结果保留最小运行记录。第一版不再设计令牌生命周期、复杂校验、精细防刷或独立安全日志体系。

### 最终技术拓扑

```text
微信群 → 固定日报填写链接 → nginx → daily-web (Vue 3)
                                      │
管理浏览器 ───────────────────────────┘
                                      │ HTTPS / API
                                      ▼
                         daily-api (Spring Boot 模块化单体)
             ┌─────────┬─────────┬────┼─────┬──────────┐
             │日报管理 │人员项目 │指标计算│规则与 AI │Quartz/报告/邮件│
             └─────────┴─────────┴────┼─────┴──────────┘
                                      ▼
                                  postgres (PostgreSQL)
                                      │             │
                                  大模型 API       公司 SMTP
```

Docker 服务固定为 `nginx`、`daily-web`、`daily-api` 与 `postgres`。大模型 API 和公司 SMTP 是外部依赖，不作为系统内部服务部署。

## 3. 后端模块清单

| 模块 | 职责与边界 |
| --- | --- |
| 日报管理 | 保存、读取和当天更新 DailyReport 与 DailyTask；校验姓名、日期、基础数据和每日唯一性。 |
| 人员/项目管理 | 维护人员基础数据（Employee）、项目基础数据（Project）及非正式项目选项，向填写、查询和分析模块提供基础数据。 |
| 数据指标计算 | 从 PostgreSQL 直接计算任务数、项目数、时段任务数、异常任务数和连续趋势等指标。 |
| 规则引擎 | 根据业务阈值和已配置分析维度输出确定性规则结论。 |
| AI 分析中心 | 调用 LLM，对任务文本和跨日报语义作解释性分析，输出建议而不改写原始数据。 |
| Quartz 定时任务 | 根据业务配置启动综合分析、报告生成和邮件发送，记录运行结果。 |
| 报告与邮件 | ReportService 生成 HTML/PDF；EmailService 通过 SMTP 投递。 |
| 系统配置 | 管理基础字典、AI 规则、Prompt、任务时间、邮件与模型配置。 |

## 4. 核心数据模型与枚举

### DailyReport 日报主表

DailyReport 为一人一天一份的主表，字段精确为：`id`、`report_date`、`employee_id`、`attendance_status`、`submitted_at`、`updated_at`、`status`。数据库唯一键为 **employee_id + report_date**。首次提交创建记录；同一人员同一日期再次填写时打开现有记录并覆盖更新当前有效日报，第一版只保留 `submitted_at` 和 `updated_at`，不引入复杂版本管理。

### DailyTask 工作任务明细

DailyTask 与 DailyReport 为一对多关系；任务数动态增加，不限制每日 1 至 6 条。字段精确为：`id`、`report_id`、`time_period`、`project_id`、`work_type`、`participation_role`、`progress_result`、`current_status`、`issue_type`、`collaboration_role`、`collaboration_requirement`。

枚举约束如下：

| 字段 | 枚举值 |
| --- | --- |
| `time_period` | `morning`（上午）、`afternoon`（下午）、`full day`（全天）、`ad-hoc time`（零散时间） |
| `participation_role` | `primary owner`（主责）、`collaborator`（协同）、`temporary support`（临时支撑） |
| `current_status` | `completed`（已完成）、`normal progress`（正常推进）、`waiting for feedback`（等待反馈）、`at risk`（存在风险）、`blocked`（已经阻塞） |

`issue_type`、`collaboration_role` 和 `collaboration_requirement` 仅在异常任务时填写。`progress_result` 用于记录工作进展和产出。

### 人员、项目与非正式项目

人员基础数据（Employee）至少包含：`id`、姓名、所属小组、人员类型/岗位、是否在岗。项目基础数据（Project）至少包含：`id`、项目名称、客户名称、所属行业、项目阶段、项目负责人、优先级、项目状态、项目编码（可为空）。第一版由唯一管理员维护。

填写页仅选择项目；行业、负责人、阶段和优先级由后台自动关联。为覆盖售前或非编码工作，项目选择中提供六个非正式选项：`customer expansion`（客户拓展阶段）、`no formal project`（暂无正式项目）、`internal initiative`（内部专项）、`department routine work`（部门日常工作）、`training/learning`（培训学习）、`other`（其他）。

## 5. 日报页面与当天修改流程

`/report` 页面按以下结构组织：

1. 每日工作日报：日期、姓名、出勤状态；
2. 工作任务卡：时段、项目/专项、工作类型、主责/协同、工作进展与产出、当前状态；
3. 当状态异常时，显示问题类型、需要协同角色、风险及协同需求；
4. “+ 新增工作任务”：按当天实际事项动态增加 DailyTask；
5. 其他补充（选填）和“提交今日日报”。

页面不使用上午、下午两个大文本框；每条任务自行选择时段。员工当天再次进入 `/my-report` 时，系统按姓名和日期查询该 DailyReport，显示已存主表和 N 条 DailyTask，允许修改后覆盖更新。当日以外日报保持只读，一人一天仅一份有效日报。

## 6. 四维 AI 分析与混合职责

AI 分析中心至少支持四个维度：

| 维度 | 分析内容 |
| --- | --- |
| `personnel dimension`（人员维度） | 当日工作负荷、工作饱和度、多项目并行、任务切换、主责/协同分布和连续工作趋势。 |
| `project dimension`（项目维度） | 当前推进状态、新增/持续/深化/完成、连续等待反馈、疑似停滞、风险归纳和多人协同。 |
| `resource dimension`（资源维度） | 缺少资源的项目、缺少的角色、高负荷人员、可调配空间和资源调配建议。 |
| `report quality`（日报质量） | 漏填、上午/下午任务缺失、描述模糊、缺少进展结果、异常任务未说明原因。 |

职责严格分离。**program rules** 直接从数据库计算：是否填写、任务数、项目数、上午任务数、下午任务数、异常任务数、连续支撑天数、连续等待反馈天数、多人参与项目和多项目并行。阈值及是否启用由业务配置决定。

**LLM semantic analysis** 处理任务复杂度、综合负荷判断、项目是否真实推进、风险语义归纳、多人是否反映同一问题、资源需求识别、资源调配建议和管理总结。LLM 输出为建议，不能自动调配人员、修改项目决定或覆盖程序规则。

管道为：原始任务数据 → 指标计算 → 规则判断 → LLM semantic analysis → 综合分析结果。模型不可用时保留指标、规则结果和失败状态，不影响日报填写或当天修改。

## 7. 业务配置、定时任务、报告与邮件

系统配置中心是业务配置中心，不承担复杂安全配置。唯一管理员可维护：

- 基础字典：工作类型、项目阶段、项目状态、风险类型、协同角色；
- AI 规则：每个分析维度的启用状态和 Prompt 版本；
- Prompt / 分析规则：无需改代码即可调整文本与阈值；
- 定时任务：每日综合分析的启停、执行周期和执行时间；
- 输出开关：更新系统、更新驾驶舱、生成报告、发送邮件；
- 邮件配置：是否发送、收件人、抄送人、邮件标题模板、分析报告模板；
- AI 模型配置：模型端点、模型标识及其凭据引用。

后端内置 **Quartz**（或同类 Java 调度机制）。管理员可将每日综合分析配置为例如每天 22:00，并选择人员效能、工作饱和度、项目风险、项目进展、资源协同和资源调配等维度；调整执行时间无需修改代码。

自动化路径为：AI 分析 → 综合分析 → ReportService → **HTML/PDF** 报告 → **EmailService** → **SMTP** → 指定管理邮箱。SMTP 用户名、密码和模型密钥通过 **environment variables** 注入，不以明文存入 PostgreSQL。

## 8. 任务运行记录与管理后台

系统维护简明的 **task-run records**，字段至少包括日期、任务、开始时间、结束时间、状态、分析人数、邮件结果和错误摘要。管理端支持查看错误与 **manual retry**；重试必须以任务运行标识控制，避免重复邮件。

`/admin/*` 的第一版页面限定为：

```text
管理驾驶舱
日报管理
├─ 日报列表
└─ 工作任务明细
分析中心
├─ 人员效能
├─ 项目分析
├─ 项目风险
└─ 资源协同
基础数据
├─ 人员管理
└─ 项目管理
系统配置
├─ 工作类型
├─ AI 分析规则
├─ 定时任务
├─ 邮件配置
└─ AI 模型配置
任务记录
```

不继续向审批、绩效或客户管理能力扩展。

## 9. PostgreSQL、Docker、迁移与质量门禁

PostgreSQL 是生产权威数据源，保存 Employee、Project、DailyReport、DailyTask、基础字典、分析规则、调度配置、任务记录、分析结果与报告引用。约束至少保证 `employee_id + report_date` 唯一、任务与日报/项目引用完整、配置版本有效和任务重试幂等。

未来每个 schema 或受控数据变化必须使用有序 migration：备份/兼容性评估 → 执行 → 结构与数据校验 → 记录版本；每次都写明回滚或恢复策略。Docker 镜像使用非特权用户、最小运行依赖和健康检查，`nginx`、`daily-web`、`daily-api` 与 `postgres` 使用环境变量连接。密钥、密码、SMTP 和 LLM 凭据不写入源码、镜像层、前端 bundle 或日志。

本仓库目前没有应用清单或可运行质量脚本。实施前必须为 `daily-web` 与 Spring Boot 后端定义并实际执行 test、lint、build 命令；脚本存在并成功前，不得声称任何应用质量检查通过。
