日报AI分析系统——总体设计修改说明

请基于当前《每日报告系统设计（方案B）》进行整体简化和调整，不推翻“Web前端 + 模块化单体后端 + PostgreSQL + Docker”的总体架构，但重新聚焦实际业务需求。

一、重新定义系统定位

系统定位修改为：

部门内部轻量日报采集、AI分析及管理辅助系统。

核心目标：

员工每天通过微信群中的固定链接填写日报；
每人每天只维护一份日报；
一份日报可以包含任意多条上午、下午或全天工作任务；
系统结构化记录人员、项目、工作事项、进展和风险；
每日定时进行人员效能、项目风险、资源协同等分析；
自动生成管理视图、分析报告并发送邮件；
AI只提供分析和建议，不自动执行人员调配或项目决策。

第一阶段不建设：

员工账号体系；
多角色权限体系；
审批流；
复杂审计体系；
微服务；
n8n；
消息队列；
Kubernetes；
CRM/绩效/工时系统。
二、简化访问和安全模型

删除当前设计中过重的：

controlled collection link生命周期管理；
高熵Token及派生值设计；
link validation复杂机制；
链接级rate limit配置中心；
submission audit详细机制；
AI读取审计；
独立安全日志体系；
多层信任边界描述。

第一版只保留必要安全能力。

员工端

员工无需登录。

微信群长期固定一个地址，例如：

https://daily.company.com/report

进入以后填写：

日期；
姓名；
出勤状态；
当日工作任务。

第一版接受：

系统不能严格证明“实际填写人就是所选择的员工”。

这是内部部门工具可以接受的业务取舍。

通过：

姓名 + 日期

建立一人一天唯一日报。

如果员工当天已经提交，再次进入允许：

查看 / 修改今日日报

而不是拒绝重复提交。

管理端

只需要一个管理员账号。

例如：

/admin

支持：

用户名密码登录；
密码Hash存储；
登录Session/JWT；
修改密码；
退出登录。

无需：

RBAC；
多管理员角色；
SSO；
OAuth；
权限矩阵。

后续如果实际使用扩大，再升级。

三、前端改为一个Web工程

无需将：

01 日报填写前端
02 管理展示前端

设计成两个独立工程和Docker镜像。

建议统一为：

daily-web

一个 Vue 3 工程，根据路径区分：

/report
员工手机填写页

/my-report
日报修改页

/admin/*
管理后台

同一个前端同时适配：

手机端日报填写；
PC管理后台。

最终Docker简化为：

nginx
daily-web
daily-api
postgres
四、重点重构日报数据模型

这是本次修改最重要的部分。

当前设计不要再把“一份日报”理解为一整段原始文本。

采用：

日报主表 + 工作任务明细表

1. 日报主表 DailyReport

一人一天一条。

主要字段：

id
report_date
employee_id
attendance_status
submitted_at
updated_at
status

唯一约束：

employee_id + report_date
2. 工作任务明细 DailyTask

一份日报对应N条任务。

字段至少包括：

id
report_id

time_period
project_id
work_type
participation_role

progress_result
current_status

issue_type
collaboration_role
collaboration_requirement

其中：

time_period
上午
下午
全天
零散时间
participation_role
主责
协同
临时支撑
current_status
已完成
正常推进
等待反馈
存在风险
已经阻塞

员工页面支持：

+ 新增工作任务

当天有几项工作就新增几条，没有固定1～6条限制。

五、补充人员和项目基础数据

增加正式业务主数据。

Employee 人员表

至少：

id
姓名
所属小组
人员类型/岗位
是否在岗

第一版管理员维护即可。

Project 项目表

至少：

id
项目名称
客户名称
所属行业
项目阶段
项目负责人
优先级
项目状态
项目编码（可为空）

日报填写时员工只需要：

选择项目

后台自动关联：

行业；
项目负责人；
阶段；
优先级等信息。

同时增加几个非正式项目选项：

客户拓展阶段
暂无正式项目
内部专项
部门日常工作
培训学习
其他

解决尚未生成项目编码的售前拓展工作。

六、重新设计日报填写页面

员工每天只进入一次。

建议结构：

每日工作日报

日期
姓名
出勤状态

────────────

工作任务1

时段
项目/专项
工作类型
主责/协同

问题类型

────────────

核心原则：

不再使用“上午一个大文本框 + 下午一个大文本框”。

而是：

每条工作任务自己携带“上午/下午/全天”属性。

七、允许日报修改

删除当前文档中的：

submit-only，不允许更正。

修改为：

一人一天只有一份有效日报，但允许员工修改当天日报。

例如：

张三
2026-08-10
        ↓
17:10第一次提交
        ↓
17:40再次打开
        ↓
修改任务
        ↓
覆盖更新当前有效日报

第一版无需复杂版本管理。

只记录：

created_at
updated_at

即可。

八、AI分析中心明确业务维度

AI分析中心不要只写泛化的“处理原始日报”。

需要明确至少支持以下维度：

人员维度
当日工作负荷；
工作饱和度；
多项目并行情况；
任务切换程度；
主责/协同情况；
连续工作趋势。
项目维度
项目当前推进状态；
新增/持续/深化/完成；
连续等待反馈；
疑似停滞；
风险问题归纳；
多人协同情况。
资源维度
哪些项目缺少资源；
缺少什么角色；
哪些人员负荷较高；
哪些人员存在可调配空间；
AI资源调配建议。
日报质量
漏填；
上午/下午任务缺失；
工作描述过于模糊；
缺少进展结果；
异常任务未说明原因。
九、采用“规则 + AI”混合分析

不要让LLM负责所有计算。

程序直接计算

包括：

是否填写
任务数
项目数
上午任务数
下午任务数
异常任务数
连续支撑天数
连续等待反馈天数
多人参与项目
多项目并行情况

这些数据直接从数据库计算。

AI负责

包括：

任务复杂度
工作负荷综合判断
项目是否真正推进
风险语义归纳
多个员工是否反映同一个问题
资源需求识别
资源调配建议
管理总结

最终形成：

原始任务数据
      ↓
指标计算
      ↓
规则判断
      ↓
AI语义分析
      ↓
综合分析结果
