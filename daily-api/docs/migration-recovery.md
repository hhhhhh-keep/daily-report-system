# 数据库迁移与恢复

数据库结构只通过 `src/main/resources/db/migration/V###__*.sql` 前向演进。当前顺序为 V001 基础数据、V002 日报与任务、V003 唯一管理员、V004 分析配置与运行产物。

## 发布前

1. 对 PostgreSQL 执行一致性备份，例如 `pg_dump -Fc`，并在独立环境验证可恢复。
2. 先用同版本镜像对备份副本启动应用，确认 Flyway `validate` 和全部 migration 成功。
3. 检查磁盘空间、当前 `flyway_schema_history` 版本及新增唯一约束可能命中的重复数据。

## 发布与验证

应用启动时由 Flyway 按版本执行未应用脚本。启动后检查健康端点、`flyway_schema_history.success`、关键表与唯一约束，再执行日报保存和管理分析冒烟场景。不得手工修改已发布 migration；修正必须增加新版本。

## 恢复策略

这些 migration 包含建表和约束，默认不提供自动向下迁移。若升级失败或必须回退：停止写入，保留失败实例与日志，恢复发布前的 PostgreSQL 备份，并回滚到匹配该备份 schema 的应用镜像。若 migration 已成功且产生新业务数据，优先发布新的前向修复 migration，避免直接删除表或列。

V004 的分析运行、维度结果和邮件投递是可再生成产物；恢复备份后可安全重跑缺失日期。成功邮件以日期唯一索引保护，恢复后重跑前应先核对外部 SMTP 投递记录，避免备份时间点之后已发送但数据库尚未记录的极端情况。
